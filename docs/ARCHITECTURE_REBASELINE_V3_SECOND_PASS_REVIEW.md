## Pass 2 — governance, operations, topology, recovery, keys

`check-documentation-authority.py`, architecture inventory generation and release-freeze logic encode current #203/plan assumptions. AR-1 must switch the full authority closure atomically, not only INDEX/DEVELOPMENT_PLAN/status.

Root `IMPLEMENTATION_PLAN.md` and `PROFILE_LIFECYCLE_PLAN.md` remain current-looking; historical slice documents can contain stale policy wording. Historical truth stays, but every document that can influence implementation needs a status class.

### Recovery/keyrings already exist

Phase2I repository-local recovery is substantial. Remote production-like rehearsal is the gap.

Contact/resolver keyrings are versioned; resolver also has key reconciliation/rotation ledger. V3 standardizes lifecycle/governance and rehearses it rather than replacing cryptography.

### Operational authority is not “Python”

Current Cloudflare mutation is repository policy/generation + GitHub Actions/Environment approval + pinned Wrangler. `opsctl` therefore starts read-only with an operations authority ledger. Language replacement is not the goal.

### Runtime topology

Resolver isolation is a justified credential-security boundary and initial KEEP.

`GENERATION_VERIFICATION` Queue is a DELETE candidate because config/checkers/binding probe contain it while accepted Worker Queue messages expose IntegrationEvent/MailboxJob consumers only. AR-2 still requires proof of no external consumer.

Graph is capability-specific: OAuth/read/delta KEEP; Graph send is not implied.

## Pass 3 — frontend, contracts, research tools, Client Mail

### Frontend is already strongly modular

Sibling feature internals and alias bypass are rejected; router consumes public APIs; shared API is transport primitives; feature APIs use generated DTOs. No broad frontend rewrite.

### Target vs accepted must be machine-visible

`UI_ARCHITECTURE.md` can intentionally describe future target topology; capability matrix/inventory describe accepted behavior. Historical accepted slice docs can also carry old decisions. Add explicit document status to the existing architecture inventory rather than another registry.

### Contract inventory is incomplete, generation is not broken

Nine generated TS modules are present; existing aggregate generated-contract inventory covers seven. Client Mail send and mailbox-client-association are correctly generated by bounded generators but absent from the aggregate map. Extend existing inventory to 100%.

### `tools/` belongs in operational architecture

Runtime-bundle and fake Camouhost are synthetic evidence; fingerprint certification is bounded external research/evidence; R2 canary is ephemeral app-test-data mutation. `profile_browser.py` is direct persistent Camoufox research and must be explicitly external-research-only/hardened or retired.

`cloud_profile_smoke.py` retains an obsolete AES-GCM + mutable R2 `current.json` model while current authority uses immutable generation objects + D1 active-generation registry. It is a historical quarantine/removal candidate, not supported runtime.

### Client Mail cleanup is concrete

Read/send classifier ownership is split. Outbound Mail use-case core is sound, but Worker transport duplicates eligibility, constructs concrete D1/query/provider adapters, orchestrates source access and chooses Gmail/SMTP. Target: application source-access need, outer provider router, composition bundle, no duplicate transport authorization, existing Worker-boundary checker extended.

## Pass 4 — data classification, OAuth refresh, concurrency

### Secret “metadata” is not automatically repository-safe

`DATA_CLASSIFICATION.md` classifies mailbox secret handles, key identifiers and security configuration as sensitive. The initial phrase “metadata-only registry” was therefore too broad.

Correct model:

- **repository policy registry:** only fields explicitly safe under classification — credential/key class, owner, environment applicability, safe secret-slot names, consumers, rotation/recovery policy, evidence/classification;
- **protected live operational inventory:** actual sensitive active key/credential identity/version, opaque handles, provider/security state and other fields that improve credential targeting or expose live configuration.

`opsctl doctor` may compare protected live state to policy, but Git/evidence receives only explicitly allowed redacted/digest/status projections.

### Onboarding/Reauth state machine already exists

Mailbox domain already has versioned/CAS-governed `Pending -> Active -> ReauthRequired -> Active/Disabled/ConfigError`. Gmail/Microsoft OAuth ceremonies already bind actor/tenant/version and handle replay/expiry; no second state machine is needed.

### Refresh is implemented, but refresh concurrency is not yet proven

Resolver provider code supports Google/Microsoft refresh-token grant. Resolver operations call refresh automatically when credentials are near expiry for generic resolve/Gmail send and expose explicit Microsoft Graph refresh.

The important remaining gap is concurrency:

1. credential is loaded from encrypted record;
2. provider refresh occurs;
3. replacement access/refresh token is persisted via the ordinary encrypted-record upsert;
4. resolver schema does not expose a general credential revision used by that refresh path.

Therefore two concurrent resolves/refreshes for the same handle have no visible single-flight/CAS/fence preventing a stale provider response from overwriting a newer rotated refresh token. This is a precise AR-8 concurrency requirement, not evidence that refresh is absent.

AR-8 must make explicit and implicit refresh share one per-handle authority and permanently test races/replay. Provider invalid/revoked refresh credentials must reconcile durably to the existing application `ReauthRequired` state rather than create another lifecycle.

### Branch protection finding was rechecked

Repository rulesets endpoint returns an empty list. Branch metadata reports `main` unprotected. Direct branch-protection details are inaccessible to the integration. The finding therefore stays narrowly phrased as observable lack of branch/ruleset protection versus the documented guarded-merge process, without claiming inaccessible settings.

## Design corrections caused by repeated research

The final v3 candidate now differs materially from its first draft:

1. AR-1 is a complete mechanically checked authority transaction.
2. Existing architecture inventory is extended, not replaced by parallel registries.
3. Current/target/historical document status is machine-readable.
4. Generated-contract inventory reaches 100%.
5. Operational inventory covers scripts/tools/research executables by role/environment.
6. `opsctl` is authority/cutover-driven, not Python replacement.
7. Recovery/keyring work is convergence/rehearsal, not reconstruction.
8. Credential inventory is two-level and data-classification-driven.
9. Existing onboarding/Reauth/OAuth ceremonies are preserved.
10. Token refresh is recognized as implemented; AR-8 specifically fixes refresh concurrency/reconciliation.
11. Release is an immutable multi-component release set.
12. Runtime simplification includes historical executable quarantine.
13. Client Mail/Outbound Mail has explicit bounded cleanup tasks.
14. Existing frontend architecture and checker frameworks are preserved/extended.

## Research conclusion

The repository is healthy enough that a broad rewrite would reduce quality. The path to 10/10 is targeted: eliminate authority ambiguity, finish ownership maps, remove residual transport/wiring leakage, classify runtime/research paths, make refresh/schema/release concurrency explicit, and prove independent operational lifecycles through rehearsal/rotation/recovery.

AR-0 remains Draft until all permanent workflows pass on the final unchanged head. Every amendment invalidates prior exact-head evidence.
